# A new card, and Ethernet as far as it goes

2026-09-10. Two requests: format the new microSD so the board boots from it,
and add an Ethernet driver and see whether it gets an IP.

The card is done and the board boots from it. `curl` is installed and
working. Ethernet gets a link at 100 Mbps full duplex and stops one step
short of carrying traffic, for a reason that turns out to be a property of
the silicon — see §6.

Two of the three coherent-DMA problems from the previous day are also fixed
along the way: the platform now has a real `dma_alloc_coherent()`.

---

A 16 GB SDHC, and not blank — it arrived with a Raspberry-Pi-shaped layout
(512 MiB FAT32 at LBA 16384, 13.9 GiB Linux at 1064960), the same as the
previous card. Formatting was the request, so it was formatted; recording

## 2. Ethernet: the MAC is a DesignWare GMAC, and Linux agrees

**The finding that made this cheap.** The ESP32-P4's EMAC is a Synopsys
DesignWare GMAC, register for register. From the vendored headers:

```
0x00 MACCONFIGURATION   0x10 GMIIADDRESS   0x18 FLOWCONTROL
0x04 MACFRAMEFILTER     0x14 GMIIDATA      0x1C VLANTAG
```

which is dwmac1000's map exactly — and ESP-IDF's own field name for the
third is `emacgmiiaddr`. So mainline `stmmac` drives it with no glue file,
exactly as mainline `dw_mmc` drives the SD controller. That was static
analysis; the chip then confirmed it out of its own version register:

```
stmmaceth 50098000.ethernet: User ID: 0x11, Synopsys ID: 0x37
stmmaceth 50098000.ethernet: 	DWMAC1000
stmmaceth 50098000.ethernet: DMA HW capability register supported
stmmaceth 50098000.ethernet: device MAC address 46:4d:90:fb:5b:10
2: eth0: <BROADCAST,MULTICAST> mtu 1500 qdisc noop qlen 1000
```

**It has its own DMA — GDMA is not involved.** The EMAC's DMA is the GMAC's
*integrated* IDMAC at EMAC base + 0x1000: `dmabusmode`, `dmastatus`,
`dmaoperation_mode`, `dmain_en`, `dmarxbaseaddr`, `dmatxbaseaddr`, with
`emac_ll_reset()` poking `dmabusmode.sw_rst`. ESP-IDF drives it directly in
`esp_eth_mac_esp_dma.c` and never routes Ethernet through GDMA (0x50081000),
which is the separate general-purpose engine for SPI/I2S and friends. This is
why `stmmac` needs no glue, and also why Ethernet inherits the SD card's
coherency problem rather than escaping it.

### What the bootloader had to do

`bootloader/p4/p4_emac.c`, new, following
`emac_ll_clock_enable_rmii_input()` from ESP-IDF's
`esp_hal_emac/esp32p4/include/hal/emac_ll.h`:

| | |
|---|---|
| clock | EMAC bus clock (`SOC_CLK_CTRL1` bit 13), module reset pulsed (`LP_CLKRST` +0x4c bit 30 — the *same register* as SDMMC's reset, one bit over, so read-modify-write or Ethernet puts the card back into reset) |
| mode | `HP_SYSTEM_GMAC_CTRL0.PHY_INTF_SEL = 4` (RMII) |
| clocks | rmii/rx/tx from `pad_emac_txrx_clk`, dividers 1, `LP_CLKRST.hp_pad_emac_txrx_clk_en` selected over the two MII-only pad clocks |
| pins | seven RMII pads on IOMUX **function 3** — 50 CLK, 49 TX_EN, 34 TXD0, 35 TXD1, 28 CRS_DV, 29 RXD0, 30 RXD1 |
| mgmt | MDC on 31 and MDIO on 52 through the GPIO matrix (signals 108 out, 109 out + 107 in) — neither has an EMAC IOMUX function on this part |
| phy | reset strobe on GPIO 51 |

Two headers had to be vendored for this (`soc/hp_system_reg.h`,
`soc/gpio_reg.h`); `vendor/sync.py` records why.

It prints, and the board still boots from the card afterwards:

```
p4boot: EMAC ready: RMII, 50 MHz ref IN on GPIO50, pads 28/29/30/34/35/49/50 func 3, MDC 31, MDIO 52, PHY rst 51
```

### The MDC divider, set rather than derived

`snps,clk-csr = <5>` in the DTS, not a clock rate. stmmac normally derives the
divider from `clk_get_rate("stmmaceth")`, but the EMAC's CSR clock on this
part is SYS_CLK (`emac_ll_get_csr_clk_src` → `SOC_MOD_CLK_SYS`), and SYS_CLK
is `cpu / mem_div / sys_div` with both dividers set at run time — so no honest
fixed-clock value exists for it. 5 is `STMMAC_CSR_250_300M`, meaning CSR/124,
chosen as the *safe* divider rather than the accurate one: MDC has to stay
under 2.5 MHz and /124 keeps it there for any SYS_CLK up to ~310 MHz.

## 3. Where it stops: coherent DMA, again

`ip link set eth0 up` fails, and it fails for a reason already familiar from
yesterday:

```
coherent DMA allocations not supported on this platform.
stmmaceth 50098000.ethernet eth0: stmmac_setup_dma_desc: DMA descriptors allocation failed
up_rc=2
```

NOMMU has no second mapping available to mark uncached, so
`dma_direct_alloc()` returns NULL and `stmmac`'s descriptor rings cannot be
allocated. `dw_mmc` survives this only because 0007 open-codes a cached ring
and 0036 maintains it by hand.

### The attempt, and the measurement that killed it

`patches/linux/0038` adds `select DMA_GLOBAL_POOL` — the DMA layer's own
mechanism for exactly this, where a device tree `shared-dma-pool` becomes the
source for `dma_alloc_coherent()`. It needs somewhere genuinely coherent to
point at, and the plan was the chip's internal SRAM, on the reasoning that
internal RAM is not cached on this part: ESP-IDF calls `esp_cache_msync()`
religiously for descriptors in PSRAM and not at all for descriptors in
internal RAM, because `esp_cache_get_line_size_by_addr()` returns 0 there.

The pool came up exactly as intended:

```
OF: reserved mem: 0x4ff60000..0x4ff7ffff (128 KiB) nomap non-reusable dma-pool@4ff60000
DMA: default coherent area is set
```

and then the SD card broke, because `dma_alloc_coherent()` started succeeding,
`dw_mmc` stopped taking its cached fallback, and 0036's diagnostic fired:

```
dw_mmc 50083000.mmc: IDMAC descriptor still owned after 100 ms; transfer dropped
```

Intermittently, *after* some transfers had already worked — the signature of a
stale cache line, not of memory the DMA cannot reach. The board never reached
a login prompt. Removing the DTS node restored it exactly.

**So the premise was wrong: that SRAM is not coherent with a bus master in
this kernel.** The select is kept and is inert (with no pool declared,
`dma_alloc_from_global_coherent()` returns NULL and everything behaves as
before), because the mechanism is right and only the memory was wrong.
Whatever eventually provides genuinely uncached memory here plugs in as a
device tree node with no driver changes at all.

### The fix: the SoC has an uncached alias after all

The premise that killed the pool was *"internal SRAM is not cached"*. That was
wrong, and checking it properly is what found the real answer.

`CACHE_LL_LEVEL_INT_MEM` is **1** on the P4 — internal memory is cached by
L1, and `esp_cache_get_line_size_by_addr()` therefore returns 64 for it, not
0. So ESP-IDF *does* maintain internal-RAM descriptors, and there is no
uncached RAM to point a coherent pool at.

But two lines further down the same header:

```c
#define CACHE_LL_L2MEM_NON_CACHE_ADDR(addr) ((uintptr_t)(addr) + SOC_NON_CACHEABLE_OFFSET_SRAM)
```

and in `soc/soc.h`, commented *"non-cacheable offset for memory behind the
cache"*:

```c
#define SOC_NON_CACHEABLE_OFFSET_SRAM        0x40000000
#define SOC_NON_CACHEABLE_OFFSET_PSRAM       0x40000000
```

**Both PSRAM and internal SRAM are aliased uncached at +0x40000000.** That is
exactly what `ARCH_HAS_DMA_SET_UNCACHED` exists for — the same mechanism MIPS
uses with `UNCAC_BASE`.

It could not be tested from Linux: `/dev/mem` refuses anything past
`high_memory`, so a read of `0x88000000` returns `Bad address` from
`valid_phys_addr_range()` before it reaches the bus. The bootloader tests it
in M-mode instead (`p4_psram_alias_test()`), by writing through the alias,
reading back through the cached window, then writing a *different* value
through the cached window and reading the alias again with no cache
maintenance in between:

```
p4boot: psram alias 0x88100000: cached-sees-alias 0x11111111, alias-sees-cached 0x11111111, alias-rw 0x33333333
p4boot: psram alias: UNCACHED and coherent -- dma_alloc_coherent() can work
```

The middle number is the proof: the cached write of `0x22222222` was invisible
through the alias, so it was still sitting in the cache and the alias is
genuinely not going through it.

`patches/linux/0039` implements `arch_dma_set_uncached()` on that basis —
allocate an ordinary page, hand the CPU the aliased address, hand the device
the real one, with `arch_dma_prep_coherent()` evicting dirty lines first.
`patches/linux/0038` (DMA_GLOBAL_POOL) is dropped; the two cannot coexist,
since `kernel/dma/Kconfig` has `depends on !ARCH_HAS_DMA_SET_UNCACHED` on it.

This is the fix that matters beyond Ethernet: it gives the platform a real
`dma_alloc_coherent()`, which means 0036's hand-maintained SD descriptor ring
stops being necessary and any future descriptor-ring driver just works.

### What was left after that



Two routes, in order of how much I would trust the result:

1. **Find real uncached memory.** An uncached alias of internal SRAM, a
   cache-attribute configuration, or an SRAM region excluded from L1. If one
   exists, 0038 plus a DTS node finishes Ethernet *and* retires 0036's
   hand-maintenance for the SD card. This is worth an hour with the TRM
   before anything else, because it is the fix that makes every future
   descriptor-ring driver work.
2. **Teach stmmac to maintain its own rings**, the way 0036 taught dw_mmc.
   Considerably more invasive: dw_mmc reads descriptor status in one place,
   whereas stmmac touches descriptors throughout `stmmac_rx()`,
   `stmmac_tx_clean()` and the refill path, and every one of those needs an
   invalidate before the read and a writeback after the write. Doable,
   fiddly, easy to get subtly wrong in exactly the way that cost this project
   a day already.

Also still unknown, because `ndo_open` fails before phylink attaches: **whether
the PHY answers MDIO.** The MDIO path does not depend on the RMII reference
clock — MDC comes from the MAC's own bus clock — so that is a separate
question from whether frames can move, and it will get its own answer the
moment rings can be allocated. `snps,clk-csr` is the first thing to vary if
the answer is no.

## 6. Ethernet, continued: why there is still no IP

Everything up to the data path works, and each piece was proven separately
rather than inferred:

| | evidence |
|---|---|
| MAC identified | `User ID: 0x11, Synopsys ID: 0x37`, `DWMAC1000` — read from the block's own version register |
| reference clock | `p4boot: emac: GPIO50 toggling (1867/4000 high)` — sampled as a GPIO before the EMAC claims the pad |
| MDIO | `p4boot: emac: PHY at addr 1: id 0x02430c54, bmsr 0x7849 (CR5 = CSR/124)` — bootloader reads the ID registers directly |
| PHY driver | `eth0: PHY [stmmac-0:01] driver [ICPlus IP101G] (irq=POLL)` |
| link | `eth0: Link is Up - 100Mbps/Full - flow control rx` |
| interrupt | `23: 1 ESP32P4-CLIC 23 Level eth0` — delivered on the slot the DTS asks for |

Then transmit stalls:

```
eth0: NETDEV WATCHDOG: CPU: 0: transmit queue 0 timed out 5004 ms
eth0: Reset adapter.
udhcpc: broadcasting discover          (x8, then "no lease, failing")
```

and `/proc/interrupts` for eth0 stays at **1** — 2 with an edge-triggered
slot — while systimer, UART and dw-mci all climb into the hundreds. So the
MAC asserts once and never again, NAPI never runs again, TX is never reaped,
and the watchdog resets the adapter every five seconds forever.

### It is not the DMA, and it is not PSRAM — a correction

An earlier version of this section claimed the EMAC's DMA cannot reach PSRAM,
inferred from ESP-IDF allocating its EMAC buffers with `MALLOC_CAP_INTERNAL`
and from `soc_caps.h` carrying `SOC_SDMMC_PSRAM_DMA_CAPABLE` with no EMAC
equivalent. **That inference was wrong.** `soc_caps.h` also carries a blanket
`SOC_PSRAM_DMA_CAPABLE` for this chip, and nothing anywhere in ESP-IDF says
the EMAC is restricted; IDF's choice of internal RAM is most likely latency.

Patch 0040 made `/dev/mem` reach peripheral space, and the registers settle
it. Every line below is read off the running board, not reasoned about:

| what | register | value | reading |
|---|---|---|---|
| DMA using PSRAM | `TXDESCLISTADDR` | `0x48ae4000` | ring is in PSRAM |
| …and walking it | `CURHOSTTXDESC` | `0x48ae4100` | 8 descriptors in |
| …and fetching from it | `CURHOSTTXBUF` | `0x48d52802` | a PSRAM buffer |
| bus errors | `DMA_STATUS`, `AHBORAXISTATUS` | no FBI, EB=0, 0 | none |
| dropped frames | `MISSEDFRAMECNT` | `0` | none |
| receive filter | `MACFRAMEFILTER` | `0x00000000` | broadcast **not** disabled |
| MAC enabled | `MACCONFIG` | `0x0041cc0c` | RE and TE both set |
| interrupts enabled | `DMA_INTEN` | `0x0001a061` | NIE, AIE, TIE, RIE on |
| line stuck high? | `MAC_INTSTATUS`, `DMA_STATUS` | `0`, NIS=0 AIS=0 | nothing pending |

**The EMAC's DMA reads and writes PSRAM without complaint.** The descriptors
even come back correctly cleaned (`des0 = 0`, OWN clear) after transmission,
and one run sent 8 packets with zero errors and zero drops.

### What it actually is: the interrupt asserts once

`/proc/interrupts` for eth0 reaches **1** and stops, while systimer, UART and
dw-mci climb into the hundreds. Without a second interrupt NAPI never runs
again, so transmit completions are never reaped — hence the watchdog — and
the receive ring is never drained, which is why RX sits at 1–3 packets and
`MISSEDFRAMECNT` stays 0: the ring still has room, nobody is emptying it.

Ruled out, each by experiment rather than argument:

* **CLIC slot** — tried 23 and 19, identical.
* **Trigger type** — `LEVEL_HIGH` gives 1 interrupt, `EDGE_RISING` gives 2.
* **INTMTX source** — 92 is `ETS_ETH_MAC_INTR_SOURCE`, recounted from the
  enum, and it is exactly what ESP-IDF's own driver passes to
  `esp_intr_alloc()`.
* **A stuck line** — there is nothing pending to hold it high.
* **The MAC being masked** — `DMA_INTEN` says otherwise.

### Where to go next

Instrument stmmac itself. Every register the hardware exposes says it is idle
and content, so the remaining question is on the driver side: does
`stmmac_interrupt` run a second time at all, does NAPI complete, and is
`stmmac_enable_dma_irq` reached? A print in each answers it in one build, and
nothing short of that will.

Worth trying alongside: the TX coalescing path. stmmac only sets "interrupt
on completion" every `tx_coal_frames` descriptors and relies on an hrtimer to
reap the rest, so a suspicion worth testing is that neither the IC bit nor
the timer is firing here.

## 7. What else came out of the network work

**`curl` 8.20.0 with TLS**, 1.4 MB static, comfortably under the 4 MB bFLT
exec ceiling:

```
curl 8.20.0 (riscv32-buildroot-linux-uclibc) libcurl/8.20.0 mbedTLS/3.6.6 zlib/1.3.2
Protocols: dict file ftp ftps gopher gophers http https imap imaps ... 
Features: alt-svc AsynchDNS HSTS HTTPS-proxy IPv6 Largefile libz SSL threadsafe
```

**Five busybox applets that were missing, one of them load-bearing.** DHCP
was failing for a reason that had nothing to do with Ethernet:

```
udhcpc: executing /usr/share/udhcpc/default.script deconfig
sh: can't execute 'mktemp': No such file or directory
```

Buildroot's own udhcpc script builds `resolv.conf` through a temporary file,
so the client died in its config script before ever assigning an address —
while every symptom pointed at the driver. `CONFIG_MKTEMP` is now on, along
with `FEATURE_FANCY_PING` (without it `ping -c 3` is parsed as a request to
resolve the host `-c`), `find`, `time` and `nslookup`.

**`CONFIG_IP_PNP`**, the kernel's own `ipconfig` (`net/ipv4/ipconfig.c`), so
`ip=dhcp` on the command line works. Userspace `udhcpc` remains the normal
path; this costs about 8 KB.

**`/etc/network/interfaces`** in the overlay with a carrier wait, because the
IP101G takes ~2.5 s to autonegotiate and nothing in `ifup` blocks on it — a
DISCOVER sent in that window goes into a dead cable. Note it does **not** run
at boot yet: there is no `S40network` in this rootfs
(`BR2_PACKAGE_IFUPDOWN_SCRIPTS` is off), which is a one-line fix for whenever
the data path works.

### And a correction to yesterday

Cutting the NOMMU user pool from 10 MB to 6 MB to make `MemTotal` look better
was the wrong trade, and it is reverted. 6 MB survives a login shell and a
couple of commands and runs out on anything real — an ordinary pipeline with
two command substitutions is five concurrent busybox images at 620 KB each,
and once the pool is gone the buddy allocator cannot find 620 KB contiguous:

```
nommu: Allocation of length 634880 from process 131 (exe) failed
Normal: ... 6*512kB 0*1024kB 0*2048kB = 9248kB
```

Nine megabytes free and not one block big enough. `MemTotal` is back to
16,784 kB from 21,912 kB, and that is the right way round. The real memory
win of the previous day was moving the root filesystem off the initramfs,
which freed 8 MB of unevictable page cache — not the pool.

Several apparent board failures during this work were also the test harness
rather than the board: command substitutions exhausting the pool, and a
sentinel string that matched the shell's echo of a command instead of its
output.
