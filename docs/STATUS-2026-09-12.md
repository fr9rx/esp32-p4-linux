# 2026-09-12 — PSRAM at 200 MHz

`CONFIG_SPIRAM_SPEED` is now **200**, up from 80. This had been open across
several sessions with a precise, misleading symptom recorded against it. It
was two independent bugs stacked on top of each other, and because either one
alone produced total corruption, fixing one looked like no progress at all.

Neither was in the chip or the board.

**[`PSRAM-200MHZ.md`](PSRAM-200MHZ.md) is the full write-up** — the whole
investigation, every measurement, the dead ends, and a reproducible
configuration. This page is the summary.

## Bug 1 — the tuning discarded its own result

`bootloader/sdkconfig.h` never defined `CONFIG_SPIRAM_MODE_HEX`. It has
exactly one consumer:

```c
/* mspi_timing_tuning_configs.h */
#define MSPI_TIMING_PSRAM_DTR_MODE   CONFIG_SPIRAM_MODE_HEX

/* mspi_timing_tuning.c, s_select_best_tuning_config() */
uint32_t best_point = 0;
...
#if MSPI_TIMING_PSRAM_DTR_MODE
    best_point = s_tuning_cfg_drv.psram_select_best_tuning_config(...);
#elif MSPI_TIMING_PSRAM_STR_MODE
    best_point = ...
#endif
    s_tuning_cfg_drv.psram_set_best_tuning_config(timing_config, best_point);
```

An undefined identifier in `#if` is 0, silently. Both branches vanished,
`best_point` kept its initialiser, and the tuning always selected config
index 0 — for the DQS phase pass and the delayline pass alike. The sweep
still ran, still measured a good eye, still printed it, and then threw the
answer away.

Measured at 200 MHz, delayline index against bytes wrong out of 128, at the
chosen phase of 67.5°:

```
 id     0   1   2   3   4 ... 27   28  29  30
bad    81  56  18   5   0 ...  0   17  34  65
          ^^ index 0: what was actually in use
                      ^^^^^^^^^^ the eye that was measured and discarded
```

At 80 MHz index 0 lands inside the eye, so the bug was invisible: PSRAM
worked, the walking-address test passed over all 32 MB, and nothing hinted
that the tuning result was being ignored.

It is a real IDF Kconfig symbol (`SPIRAM_MODE_HEX`, `default y` for P4). The
hand-written `sdkconfig.h` simply never had it.

## Bug 2 — no burst writes while the core is at 40 MHz

With bug 1 fixed, reads were clean and writes were not. The split was sharp:

| what | result at 200 MHz |
|---|---|
| reads of data written at 20 MHz during tuning | 0 of 128 bytes wrong |
| MR0/MR4 mode-register writes | land correctly, readback proves it |
| 16 separate uncached 4-byte stores | 0 of 64 bytes wrong |
| first 64-byte cache-line writeback | 48 bytes land, then it stops |
| every writeback after that | nothing lands at all |
| single uncached stores after that | nothing lands either |

No error flag: `SPI_MEM_S_INT_RAW` read `0x18` — `SLV_ST_END | MST_ST_END`,
"transaction ended" — before and after, with no TX underflow, no AXI error.
Raising the CPU afterwards did not recover it. The wedge is permanent for the
rest of the boot.

The bootloader ran its walking-address test *before* raising the CPU, on
purpose, so that train–map–verify all happened at one core clock. A PSRAM
burst cannot be paused once started, so write data has to arrive from the AXI
side at the bus rate — 800 MB/s at 200 MHz — and a 40 MHz core cannot feed
it. At 80 MHz the ratio is survivable, which is why this never showed up.

The raise now sits between training and the first test. The window is narrow
and both edges are load-bearing:

- **after** training — IDF's own order (`esp_psram_chip_init()` at
  `cpu_start.c:645`, `esp_clk_init()` at 830), and training at 360 MHz
  produced a PSRAM that answered every read with the halfwords swapped;
- **before** any burst write — this bug.

## What was ruled out, each measured on hardware

Worth recording, because most of the time went here and all of it was wrong:

- **Dummy cycles, both controllers.** MSPI_ID_2 swept wr 2..24 × rd 10..40
  with variable dummy on and off: zero matches. MSPI_ID_3 swept rd 16..36:
  completely flat, ~41 of 64 bytes wrong at *every* value. The dummy
  registers have no effect while variable dummy derives the count from DQS.
- **Buffer alignment.** Stack and static buffers fail identically.
- **Pin drive strength** 0..3, **split transactions** on/off, **page size**
  1024/2048, **bus divider** 2..6: no change.
- **Stale tuned state.** Re-applying the tuned registers, and re-running the
  entire tuning and replaying at once, both still failed.
- **MPLL.** `clk_ll_mpll_set_config` computes `div = 400/20 - 1 = 19`,
  `40 × 20 / 2 = 400 MHz`. Correct.
- **Vendored sources.** `esp_psram_impl_ap_hex.c`, `mspi_timing_tuning.c`,
  `mspi_timing_by_dqs.c` and `mspi_timing_tuning_configs.h` all diff clean
  against `C:/esp/v6.1-beta1/esp-idf`. The bug was never in the code we
  copied; it was in the configuration we wrote around it.

A caution about instruments, again. Several of those sweeps measured nothing
at all: the first write round trip after init returned 16 bad and every one
after it returned 64, so whatever was being swept, the output looked like
`16 64 64 64 64`. That shape was the wedge, not the knob. Counting bad bytes
also conflates "the data is late" with "the data is wrong" — switching to
*where does `ref[0]` appear* is what made the 14-byte offset legible.

## Verification

- Bootloader walking-address test over all 32 MB: passes, **9 cold boots out
  of 9**, at 200 MHz with the CPU at 360.
- Kernel and DTB CRC32 after the copy into PSRAM: match flash.
- Linux boots to userspace; `memtester 6M 1` completes with no failures.
- `md5sum` of a 4 MB tmpfs file, twice: identical. SD reads: identical.
- DHCP `192.168.1.20`, gateway ping 0% loss at ~1.1 ms.
- `dmesg` matches of oops/panic/segfault/bad page/corrupt: **0**.

Throughput, same command and same harness either side of the change:

| | 80 MHz | 200 MHz |
|---|---|---|
| `memtester 6M 1` | 159.2 s | **104.4 s** |

## Also changed

`bootloader/Makefile` now fails the build if `bootloader.bin` exceeds 24576
bytes. We are written at `0x2000` and the partition table lives at `0x8000`;
espflash will write straight through the table, and the failure arrives one
boot later as `no kernel partition (type 0x40)`, which reads like a
partition-table problem and is not one. A diagnostic build overran it by 96
bytes during this session and cost a confusing reflash.

## Still open

- `CONFIG_ESP_REV_MIN_FULL` is undefined, so `HAL_CONFIG(CHIP_SUPPORT_MIN_REV)`
  is 0. That happens to select the right paths for rev 1.0 silicon — the
  MSPI wakeup workaround in, the rev-3-only AXI weight arbiter out — but it
  is the same class of accident as bug 1 and should be defined as 100.
  `-Wundef` lists the rest; most are other targets and harmless.
- 250 MHz is rev-3-only in IDF (`SPIRAM_SPEED_250M` depends on
  `!ESP32P4_SELECTS_REV_LESS_V3`). This board is rev 1.0, so 200 is the
  ceiling here.
- Bootloader step 12 (SD high speed) and warm-reset flash instability are
  unchanged from the previous session.
