# Status — 2026-09-11

Ethernet works end to end. This document is about how, because the symptom
pointed hard at the wrong thing for most of a day and the record of what was
ruled out is worth more than the fix, which is four device-tree properties.

Previous: [`STATUS-2026-09-10.md`](STATUS-2026-09-10.md).

## 2. The bug

**Transmit stopped after a handful of packets and the netdev watchdog reset
the adapter every five seconds.**

```
eth0: NETDEV WATCHDOG: CPU: 0: transmit queue 0 timed out 5644 ms
eth0: Reset adapter.
```

Small frames went out fine — seven 86-byte frames transmitted and completed
cleanly. A 342-byte DHCP DISCOVER wedged it. So the board could receive the
whole LAN's broadcast traffic and still never obtain an address.

### What the hardware was actually doing

Sampling the DMA every ~0.4 s across the pre-watchdog window, through
`/dev/mem` (patch 0040):

```
s0  DMASTAT=0x00660404 CURTX=0x48b040e0 tx=8 bytes=680  inflight=0
s1  DMASTAT=0x00660000 CURTX=0x48b04100 tx=9 bytes=1022 inflight=342
s2  DMASTAT=0x00360000 CURTX=0x48b04120 tx=9 bytes=1022 inflight=342
s3  DMASTAT=0x00360000 CURTX=0x48b04120 tx=9 bytes=1022 inflight=342
...  unchanged until the watchdog fires
```

Two numbers carry it:

- **`DMASTAT` bits 22:20 = TS = 3**, which in DWMAC1000 is *"Running: reading
  data from host memory buffer and queuing it to the transmit buffer (Tx
  FIFO)"*. Not stopped, not suspended, not errored — parked mid-fetch, and it
  never leaves. `CURHOSTTXBUF` held `0x48d6a002` the whole time.
- **BQL `inflight` stuck at 342**, the size of the DISCOVER. That is what
  holds `netif_xmit_stopped()` true, which is the only thing `dev_watchdog()`
  looks at.

No error bit is set anywhere: no fatal bus error, no underflow, `EB = 0`,
`AHBORAXISTATUS = 0`, `MISSEDFRAMECNT = 0`.

### The cause

stmmac had turned on **store-and-forward in both directions**. Nothing in the
device tree asked for it; `stmmac_dma_operation_mode()` chooses it on its own:

```c
} else if (priv->plat->force_sf_dma_mode || priv->plat->tx_coe) {
        txmode = SF_DMA_MODE;
        rxmode = SF_DMA_MODE;
```

`dma_cap.tx_coe` is set on this block — the chip reports TX checksum offload —
and that alone is enough.

Store-and-forward means the DMA pulls the entire frame into the FIFO before
the MAC begins transmitting. **The FIFOs on this part are a few hundred
bytes.** ESP-IDF says so itself, in a comment on the very same register, in
`emac_hal_init_dma_default()`:

```c
    /* Disable Receive Store Forward (Rx FIFO is only 256B) */
    emac_ll_recv_store_forward_enable(hal->dma_regs, false);
    ...
    /* Disable Transmit Store Forward */
    emac_ll_trans_store_forward_enable(hal->dma_regs, false);
```

An 86-byte frame fits. A 342-byte frame does not, and the transfer never
completes. That is exactly why the failure looked size-dependent and random
rather than like a mode error.

### The fix

Four properties on the `ethernet@50098000` node, each mirroring a line of
IDF's own DMA setup:

| property | register effect | IDF equivalent |
|---|---|---|
| `snps,force_thresh_dma_mode` | TSF = 0, RSF = 0, threshold 64 | `trans/recv_store_forward_enable(false)` |
| `snps,aal` | AAL, address-aligned beats | `addr_align_enable(true)` |
| `snps,mixed-burst` | MB | `mixed_burst_enable(true)` |
| `snps,no-pbl-x8` | PBL stays 8 beats, not 8×8 | IDF never sets PBLx8 |

The first is the one that matters; the other three are matched to IDF because
that is the combination the vendor validates. Readback confirms they land:

```
BUSMODE   0x01900880 -> 0x06900880    (AAL+MB set, PBLx8 cleared)
DMAOPMODE 0x02202006 -> 0x00002002    (TSF and RSF cleared)
```

Threshold mode starts transmitting once 64 bytes are in the FIFO and streams
the rest, which is what a FIFO this small requires — and it is how IDF has
always driven this block.

## 3. What was not the cause

Every one of these was measured on hardware, not argued about. Recorded so
nobody re-runs them.

| suspected | measurement | verdict |
|---|---|---|
| DMA cannot reach PSRAM | `TXDESCLISTADDR 0x48ae4000`, DMA walked 8 descriptors in, fetched buffers from PSRAM | reads PSRAM fine |
| bus errors | no FBI, `EB = 0`, `AHBORAXISTATUS = 0` | none |
| dropped frames | `MISSEDFRAMECNT = 0` | none |
| receive filter | `MACFRAMEFILTER = 0`; promiscuous made no difference | broadcast not blocked |
| MAC disabled | `MACCONFIG = 0x0041cc0c`, RE and TE set | enabled |
| interrupts masked | `DMA_INTEN = 0x0001a061` — NIE, AIE, TIE, RIE | enabled |
| CLIC slot | tried 23 and 19 | identical |
| trigger type | LEVEL_HIGH vs EDGE_RISING | identical |
| INTMTX source | 92 is `ETS_ETH_MAC_INTR_SOURCE`, what IDF allocates | correct |

Two claims made along the way were wrong, and both are worth stating plainly
because each cost hours:

- **"The EMAC's DMA cannot reach PSRAM."** Inferred from IDF allocating
  buffers with `MALLOC_CAP_INTERNAL` and from `soc_caps.h` carrying
  `SOC_SDMMC_PSRAM_DMA_CAPABLE` with no EMAC equivalent. The register dump
  disproves it, and `soc_caps.h` also carries a blanket
  `SOC_PSRAM_DMA_CAPABLE` for this chip. IDF's choice is most likely latency.
- **"The interrupt asserts once and never again."** This came from
  `awk '/ 23:/{print $1, $2}' /proc/interrupts`, which matches on the *Linux
  virq* column, not the hardware slot. Receive interrupts were running the
  whole time; `rx_packets` climbing 1 → 3 → 4 → 5 → 12 in the same session
  said so, and was in the logs unread. **The measurement was fine; the
  instrument was wrong.**

## 4. The MAC address

stmmac reads `MACADDRESS0` at probe (`stmmac_get_umac_addr`), found
`0xFFFFFFFF` because nothing had ever written it, and fell back to
`eth_hw_addr_random()`:

```
stmmaceth 50098000.ethernet: device MAC address 6e:43:38:27:a2:75
```

A different locally-administered address on every boot — hence a new DHCP
lease each time and no way for anything on the LAN to recognise the board
twice.

The real address is in eFuse BLOCK1 and it belongs to Ethernet. ESP-IDF's
`Kconfig.mac` for this target:

> On ESP32-P4 this value is fixed to one, because only Ethernet receives a
> universally administered MAC address.

and it is derived by adding 0 to the base MAC, so the base address *is* the
Ethernet address — exactly what espflash prints.

Byte order, measured rather than assumed. espflash reports
`60:55:f9:fb:0c:31`; the two eFuse words read back as

```
EFUSE_RD_MAC_SYS_0  0xf9fb0c31      EFUSE_RD_MAC_SYS_1  0x00006055
```

so the address is stored big-endian across the pair: the OUI in the high half
of word 1, the remaining four bytes in word 0 most-significant first. The
DWMAC registers are the other way round — `ADDRLOW[7:0]` is the first byte on
the wire — which is the shuffle in `p4_emac.c` step 7, and it matches
`stmmac_get_mac_addr()`, the code that reads it back. A blank part reads all
zeroes and is left alone, so stmmac's random fallback still applies rather
than putting `00:00:00:00:00:00` on the wire.

Result:

```
p4boot: EMAC station address 60:55:f9:fb:0c:31 (eFuse)
...
eth0      Link encap:Ethernet  HWaddr 60:55:F9:FB:0C:31
```

## 5. Bringing the interface up at boot

`BR2_PACKAGE_IFUPDOWN_SCRIPTS` was off, so there was no `/etc/init.d/S40network`
and nothing brought `eth0` up. It is on now.

The overlay's `/etc/network/interfaces` also had a real bug. It waited for
carrier in `pre-up`, but ifupdown runs `pre-up` **before** it brings the
interface up, and reading carrier on a down interface does not return 0:

```
# cat /sys/class/net/eth0/carrier
cat: read error: Invalid argument
```

so the loop never saw carrier, burned its whole timeout every boot, and then
handed udhcpc the same dead cable it existed to avoid. It now does the
`ip link set eth0 up` itself first, which makes the wait mean something.
Doing it twice is harmless.

Boot sequence now, unattended:

```
uptime 8.90    192.168.1.0/24 dev eth0 scope link  src 192.168.1.28
uptime ~19     inet addr:192.168.1.28   default via 192.168.1.1 dev eth0
```

One trap worth writing down: **busybox `udhcpc` daemonises unless given
`-f`**, and once daemonised it logs to syslog, of which there is none here.
Run without `-f` it prints nothing, returns 0 immediately, and looks exactly
like a silent failure. Several minutes went into that.

## 7. Still open

- **`curl` fails with exit 27 (out of memory) on every transfer.** `curl
  --version` works and reports `curl 8.20.0 ... mbedTLS/3.6.6 zlib/1.3.2`, and
  busybox `wget` downloads 5 MB over the same stack without trouble, so this
  is a NOMMU allocation problem in curl, not a network one. Not investigated.
- **busybox `wget` cannot do HTTPS** (`not an http or ftp url`) — no TLS in
  this busybox build. curl is the intended TLS client, hence the above.
- **`time` reports nonsense user time** (`user 3688899688h 40m 32s`). Real
  time is right. Some `getrusage`/clock path is wrong; harmless but wrong.
- 10 Mbit/s links will not work. ESP-IDF reprograms an ESP-specific RMII
  clock divider on speed change (`RMII_CLK_HZ / RX_TX_10M_SPEED_CLK_HZ - 1`
  = 19); stmmac knows nothing about it and the bootloader sets the 100 Mbit/s
  value once. Only matters against a 10 Mbit/s peer.
- Bootloader step 12 (SDMMC high speed), 200 MHz PSRAM, and warm-reset flash
  instability are unchanged from `STATUS-2026-09-10.md`.
- Nothing is committed, in either repository.
