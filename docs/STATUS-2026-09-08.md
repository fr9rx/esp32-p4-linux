## Bootloader: steps 7 through 11 are done

| step | what | state |
|---|---|---|
| 7 | partition walk + `esp_rom_spiflash_read` + CRC32 in place | done, CRCs match host |
| 8 | copy to PSRAM, CRC the copies | done, matches the pre-tuning CRC |
| 9 | jump to `stub.S` to prove the handoff | done: hartid 0, dtb pa, pc `0x48000050` |
| 10 | jump to Linux | done, earlycon onward |
| 11 | LDO4 3.3 V + SDMMC clocks + slot-0 IOMUX | done, card enumerates |
| 12 | SDMMC high speed | not attempted |

Three things found on hardware that were not in the plan:

**The ROM's flash chip_size is 2 MB.** `esp_rom_spiflash_read()` range-checks
every read against `g_rom_flashchip.chip_size`, which the first stage leaves at
its 2 MB default. Reads below `0x200000` work and the first one at or above it
returns `ESP_ROM_SPIFLASH_RESULT_ERR`. The partition table parsed perfectly and
the kernel CRC died 1.875 MB in, at flash `0x00200000` exactly. IDF does the
same assignment in `bootloader_flash_update_size()`, part of the init sequence
we took over. Fixed in `p4_flash_init()`.

**The reset-reason report earns its keep.** `rtc_get_reset_reason` (ROM,
`0x4fc00018`) survives the reset it describes, and `0x07 MWDT (core)` versus
`0x01 power-on` was what turned "Linux crashes" into "Linux hangs and the
watchdog correctly resets it 30 s later" — a completely different problem.

**GPIO hangs the kernel, and both banks are now disabled in the DTS.**
`esp32p4_gpio_driver_init()` prints `gpio gpiochip0: Static allocation of GPIO
base is deprecated` and never returns. Captured with `initcall_debug`. Nothing
in this DTS consumes a GPIO and the SD node polls with `broken-cd`, so
disabling both banks costs nothing today. The DTS comment records the two
suspects worth trying first — bank 0 is the one with the CLIC irqchip, and bank
1 claims the *same* register window as bank 0.

## The root filesystem is an initramfs, not the SD card

> **Superseded in part by the addendum below.** The card has since been
> wiped and repartitioned, with permission. What still holds is the
> conclusion: the root filesystem is the built-in initramfs.

**The microSD card in the slot is a Raspberry Pi OS system disk.** `p1` is its
FAT boot partition (`LICENCE.broadcom`, `bcm2710-rpi-3-b-plus.dtb`, `overlays`,
and an `issue.txt` reading *"Raspberry Pi reference 2026-06-18 ... pi-gen ...
stage2"*); `p2` is its 116 GB root.

I did not write a single byte to it. Putting our rootfs there means
repartitioning a working install, and that is your call, not something to do
unattended. So the root filesystem is compiled into the kernel instead
(`CONFIG_INITRAMFS_SOURCE`), which needs no card at all.

The SD hardware itself is fully working — the controller comes up, the card
enumerates at 20 MHz, and both partitions mount. Only the *root* filesystem
moved.

To go back to an SD root when you have a spare card: put
`output/images/rootfs.ext4` on a partition, restore
`root=/dev/mmcblk0p1 rootfstype=ext4 rootwait` in `CONFIG_CMDLINE`, and set
`CONFIG_INITRAMFS_SOURCE` back to `""`. The bootloader neither knows nor cares.

## Known issues

**`reboot` from the shell does not come back.** It correctly triggers the MWDT
restart handler (`reset reason 0x07`), but after a *warm* reset the MSPI block
still holds the previous boot's PSRAM tuning, and the ROM's flash reads then
misbehave — first returning different wrong data on each attempt
(`0x20fa9b69`, `0x78e615df` for bytes whose real CRC is `0xc52ac046`), and now
stalling outright inside the read. A hard reset or the reset button always
clears it, and `make monitor` hard-resets anyway.

`mspi_timing_enter_low_speed_mode(true)` at the top of `p4_flash_init()` — the
same call IDF makes before tuning, which clears the tuning registers and
restores the ROM's flash clock source — was not sufficient. The bootloader now
runs a read-stability self-test (CRC the same 64 KB twice) and refuses to boot
rather than loading a corrupt kernel silently, and announces the check *before*
running it so the hang names itself:

```
p4boot: flash: checking read stability...      <- last line after a warm reset
p4boot: flash: reads are stable (...)          <- what a cold boot prints
```

Next thing to try: the flash clock source may be being restored while the PLLs
are in a different state than at cold boot, since `p4_flash_init()` runs before
`p4_clk_init()`. Moving the MSPI restore after the clock init, or re-attaching
the flash through `esp_rom_spiflash_attach()`, are the two cheap experiments.

**No `/home`.** The rootfs has no `/home`; use `/tmp` (tmpfs) or `/root`.

**200 MHz PSRAM** is still unresolved from the previous session and still runs
at 80 MHz. Unrelated to anything above; see `bootloader/sdkconfig.h`.

## Reproducing

```
cd bootloader
make                      # build the bootloader
make flash-all            # bootloader + partition table + kernel + dtb
make crc                  # the CRC32s the board should print
make monitor              # console at 4 Mbps
python ../tools/shell.py COM17 "uname -a"    # non-interactive commands
```

New in `tools/`:

- `tar2cpio.py` — buildroot `rootfs.tar` → initramfs cpio, injecting `/init`
  and the `/dev` nodes an initramfs needs. Reads the tar rather than
  `output/target` because the tar is the fakeroot-built image with correct
  ownership and modes.
- `mkdtb.sh` + `dt-include/` — build the DTB without a kernel tree. Verified to
  reproduce the committed `.dtb` byte for byte.
- `shell.py` — drive the console non-interactively (espflash's monitor is
  read-only from a script's point of view).

The kernel was rebuilt in WSL at `~/p4ev-linux/output/build/linux-custom`; the
config delta is recorded in `config/kernel.config`. `images/Image` is the older
SD-root build, kept; `images/Image.initramfs` is what boots.

# Addendum: `free`, and the SD card

Second session, same day. Two requests: add `free`, and use the SD card with
the Raspberry Pi OS removed.

## `free` — done

`CONFIG_FREE=y` in `board/busybox.fragment`, plus `CONFIG_FDISK`,
`CONFIG_FEATURE_FDISK_WRITABLE` and `CONFIG_MKFS_EXT2`, which are what let the
board partition and format its own card (there is no card reader on the host).
busybox is 599 KB as a FLAT binary, well under the 1 MB the fragment warns
about.

```
# free
              total        used        free      shared  buff/cache   available
Mem:          17168        2784        9628           0        4756        8916
```

`e2fsprogs` was wanted for a real `mkfs.ext4` and cannot be had:
`package/e2fsprogs/Config.in` has `depends on BR2_USE_MMU # util-linux/libblkid`
and this is a NOMMU build. So the card is ext2, with no journal.

## The Raspberry Pi OS is gone, and the card is partitioned and populated

```
p1  LBA      2048    1048576 sectors    512 MiB  ext2, holds the rootfs
p2  LBA   1050624  242456576 sectors  115.6 GiB  free for data, unformatted
```

Done from the board itself by `tools/sd-init.py`, in three phases so a failure
in one does not cost the others. The Pi's MBR, its FAT boot sector at sector
16384 and its ext4 superblock at sector 1064960 were each zeroed by address.
The full 4.4 MB rootfs is on p1 and lists correctly (`df`: 4.1M used of 510M).

Two things that shaped that script:

- **Small writes in bulk wedge the board.** `dd bs=512 count=8192` stalled long
  enough for the MWDT to reset it mid-run. The same 4 MiB as `bs=1M count=4`
  takes under a second. Every bulk write in the script uses `bs=1M`, and the
  one sector that must be written by hand (the MBR) is built in tmpfs first.
- **No `base64` applet**, so the MBR travels as `printf` octal escapes. Fine,
  since an MBR is almost all zeros. `partprobe` re-reads the table without the
  reboot that would otherwise land in the warm-reset flash problem.

## But the card cannot be the root filesystem yet

**This is unresolved, and it is a kernel driver bug, not a configuration
mistake.** The board still boots from the initramfs kernel, which is what is
flashed now.

The failure is precise and reproducible. With the card mounted from a working
userspace:

| operation | result |
|---|---|
| `mount -t ext2 /dev/mmcblk0p1 /mnt` | works |
| `ls /mnt` (the filesystem's root directory) | works, lists everything |
| `cat /mnt/f1` (a file in that root directory) | works, 4096 bytes correct |
| `ls /mnt/lost+found` or `ls /mnt/etc` (any subdirectory) | **never returns** |
| `dd` a whole MiB to or from `/dev/mmcblk0` raw | works, verified after `drop_caches` |

So single large contiguous requests are fine and the scattered multi-block
requests a filesystem generates are not. That points at the scatter-gather
IDMAC path — the same machinery patch 0007 touches with its "cached-descriptor
-ring IDMAC fallback", alongside `dma-noncoherent` and the riscv non-standard
cache ops from patch 0001. As root, the mount never completes at all, and
`init=/none` proved it: the kernel never reached the exec, so it is the mount
and not the first binary off the card.

Ruled out on hardware, each a separate flash-and-boot:

- **the ext4 subsystem** — it was mounting our ext2 via
  `CONFIG_EXT4_USE_FOR_EXT23` and hung on the *first write*, even 4 KB. The
  standalone `CONFIG_EXT2_FS` driver fixed writes completely, and is now what
  the kernel uses. A real find, just not the whole story.
- `broken-cd` → `non-removable`, to stop the once-a-second presence poll
  racing real I/O. No change.
- `max-frequency` 25 MHz → 4 MHz. No change. Restored to 25 MHz, the setting
  with the most successful I/O behind it.
- `rootdelay=5`, in case the mount was racing card readiness. No change.
- **PIO instead of IDMAC**, via a new `fifo-mode` DT property
  (`patches/linux/0035`). This made it *worse*: with PIO the card enumerates
  but the partition scan never finishes, dying before even printing
  `mmcblk0: p1 p2`. The property is kept because it is a useful one-line
  toggle, and it is inert unless the DTS asks for it. The DTS does not.

Where I would look next: `dw_mci_translate_sglist` / the IDMAC descriptor ring
against patch 0007, and whether the descriptor ring's cache maintenance is
correct for a multi-descriptor transfer. The distinctive `0xcccccccc` that
appeared in early reads of freshly written sectors is worth chasing too — it
looks like a buffer whose DMA never landed being returned as data.

## Where things stand

- **Board boots to a login prompt, reliably, from the initramfs kernel.**
  `images/Image.initramfs` is what is flashed and what `make flash-kernel`
  defaults to.
- **The SD card is prepared and mounts**, and its top-level directory reads
  correctly — but it is not trustworthy for real use until the above is fixed,
  and it cannot be the root filesystem.
- `images/Image` is the SD-root kernel (ext2 root, no initramfs), kept so the
  experiment is one flash away: `make flash-kernel KERNEL=../images/Image`.
