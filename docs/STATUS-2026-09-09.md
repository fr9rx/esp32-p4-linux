# The SD driver, the missing 15 MB, and hot code in SRAM

2026-09-09. Four things were asked for: fix the SD driver, give Linux the
whole 32 MB rather than 17, bring over the tool set from the hypervisor
image, and add a way to run hot kernel code from internal SRAM.

All four are done and verified on hardware. The board now boots from flash,
mounts its root filesystem from the microSD card, and keeps what you write to
it across a power cycle, with usable memory roughly doubled.

The fourth was kept separate on purpose and then measured, and the measurement
says it bought nothing on these workloads — §4 reports that rather than
burying it.

---

## 1. The SD driver: a cache line the CPU wrote to itself

**Root cause, and it is a one-line omission with a very large blast radius.**

`dw_mci_prepare_desc32()` polls the descriptor OWN bit before reusing a
descriptor, to be sure the IDMAC has finished with it:

```c
if (readl_poll_timeout_atomic(&desc->des0, val,
			      IDMAC_OWN_CLR64(val),
			      10, 100 * USEC_PER_MSEC))
	goto err_own_bit;
```

That is a plain load. It is correct upstream because the ring comes from
`dma_alloc_coherent()` and is therefore *uncached*.

On this platform it is not, and the kernel says so out loud at boot:

```
coherent DMA allocations not supported on this platform.
dw_mmc 50083000.mmc: IDMAC: cached descriptor ring with manual cache sync
```

NOMMU has no second mapping available to mark uncached, so
`dma_alloc_coherent()` fails and the fallback in
`0007-mmc-dw_mmc-esp32p4-fixes.patch` allocates the ring with
`devm_kzalloc()` — ordinary cached PSRAM. 0007 writes the ring back before
each transfer, so the IDMAC does see our descriptors. **It never invalidates,
so we never see the IDMAC's.** The poll above reads the clean, resident,
stale line the CPU wrote itself, with OWN still set, spins its full 100 ms,
and fails the transfer.

That single missing direction explains the entire symptom list from
`STATUS-2026-09-08.md`, including the parts that looked contradictory:

| observed | why |
|---|---|
| `dd bs=1M` of a whole MiB works | one transfer; `err_own_bit` reinitialises the ring, so the retry finds OWN clear |
| any subdirectory read never returns | many small requests in a burst, each paying 100 ms per descriptor |
| freshly written sectors read back as `0xcccccccc` | descriptors whose DMA never ran — exactly the guess in the previous status doc |
| PIO (`fifo-mode`) was *worse* | a different path with its own problem; it was never the same bug |

`patches/linux/0036-mmc-dw_mmc-idmac-descriptor-ring-coherency.patch` adds the
missing direction: invalidate the ring before the OWN-bit polls, and write it
back at the end of `dw_mci_idmac_init()` so the chain pointers reach memory
and every line is left clean — which is what makes a whole-ring invalidate
lossless. Both are gated on a new `sg_cpu_cached` flag, so a platform with a
real coherent allocation is untouched. The `dev_dbg()` on the timeout became
a ratelimited `dev_warn()`, because a bug that only makes things slow needs to
announce itself.

### Root on the card, and it survives a power cycle

```
[    1.023864] VFS: Mounted root (ext2 filesystem) on device 179:1.
[    1.040634] Run /sbin/init as init process
p4ev login:
```

```
# uname -a > /root/proof.txt; sync
--- DTR/RTS hard reset, p4boot: reset reason 0x01 (power-on) ---
# cat /root/proof.txt
Linux p4ev 6.18.35 #7 Wed Sep  9 22:44:23 +03 2026 riscv32 GNU/Linux
# cat /data/x.txt
second file
# dmesg | grep -c -e 'still owned' -e 'I/O error' -e 'EXT2-fs error'
0
```

Write throughput with root on the card, measured:

| test | result |
|---|---|
| 4 MB, `bs=64k conv=fsync` | 2 s (~2 MB/s) |
| 1 MB, `bs=4k conv=fsync` (256 requests) | 1 s |
| OWN-bit timeouts across all of it | 0 |

**Writes are fine.** An earlier read of this was wrong and worth recording:
`mkfs.ext2` and a large `cp -a` did stall for minutes and trip the watchdog,
and it looked like a surviving write-path bug. It was not — it was memory
pressure specific to the *initramfs* kernel, where the 8.4 MB rootfs sits in
RAM as unevictable page cache. See §5.

## 2. The missing 15 MB was never missing, but 4 MB of it is now back

The DTS always described all 32 MB, and Linux always saw it:

```
Memory: 14180K/32768K available (..., 18360K reserved, ...)
```

`free` showed 17 MB because `MemTotal` excludes two things:

* **10 MB** of `no-map`, non-reusable reserved memory for the NOMMU
  user-space mmap pool (patch 0010). Subtracted from `MemTotal` one byte for
  one and unusable for anything else, ever.
* **~5.3 MB** of non-freeable kernel image.

The pool exists for a real reason — NOMMU satisfies every mmap from *one*
physically contiguous range, and buddy fragments fast on a 32 MB machine — so
it cannot simply go. CMA would give both properties at once, accounted *and*
contiguous, but `config CMA depends on MMU`, which is precisely why patch
0010 exists.

So: measure, then resize. The largest binary on the image is `as` at 1.4 MB
(`objcopy` 1.1 MB, busybox 588 KB), and every one of those goes through the
pool — it backs `binfmt_flat` exec, not just anon mmap, because patch 0010
hooks `do_mmap_private()`. 6 MB is four times the largest single thing that
asks, which is comfortable with root on the card and *not* comfortable with an
8.4 MB initramfs; §5 is what the second case looks like.

The top edge stays pinned at `0x4A000000`. Three things moved the number, and
the second is by far the biggest:

| | `MemTotal` | available | reserved |
|---|---|---|---|
| before (10 MB pool, initramfs root) | 17,208 kB | 8,916 kB | 18,360 K |
| pool 10 → 6 MB | 21,256 kB | 8,516 kB | 16,688 K |
| **+ root on the card, no initramfs** | 21,248 kB | **17,264 kB** | 12,092 K |
| **+ `!RELOCATABLE`** (§4) | **21,912 kB** | **17,696 kB** | 11,000 K |

**Usable memory roughly doubled: 8.9 MB → 17.7 MB.** Most of that is not the
pool at all — it is §1. An initramfs root keeps the whole 8.4 MB rootfs
pinned in RAM as unevictable page cache forever; moving it to the card hands
all of it back. The three requests really were one change.

**The pool is a partition, not a leak.** Linux has all 32 MB; 6 MB of it is
spoken for by an allocator `free` cannot see, and that 6 MB is what lets
programs start at all. Shrinking it further trades exec headroom for a
cosmetically larger `MemTotal` — see §5 for what that failure looks like.

## 3. The hypervisor image's tool set, on the native image

The two userspace configs had genuinely diverged. Comparing package sets
rather than guessing:

* the **hypervisor guest** had 17 packages the native image lacked
* the **native image** had `binutils` (`as`, `objcopy`), which the hypervisor
  guest lacked — and which the whole on-board assembly goal depends on

The union is the right target, so the native image gained all 17 and kept
binutils:

```
bc  bzip2  diffutils  grep  less  memtester  nano  ncurses  sed  tree
which  xz  dhrystone  whetstone  busybox-show-others  host-mkpasswd
```

Verified on the board:

```
# for t in nano less grep sed bc tree which xz bzip2 diff memtester as objcopy lua; \
    do command -v $t >/dev/null && printf '%s ' $t; done; echo
nano less grep sed bc tree which xz bzip2 diff memtester as objcopy lua
```

`memtester` is the one worth calling out: this board now has an on-board
PSRAM tester, which is the tool the 200 MHz PSRAM question has been missing.

The rootfs went **4.4 MB → 8.4 MB**, and that is affordable precisely
*because* of §1 — the root filesystem lives on the card, so rootfs size no
longer costs RAM. The three requests turn out to be one change.

`find` is not built in this busybox and `time` is not either; both are one
line in `board/busybox.fragment` if wanted.

### Flash layout moved

The initramfs kernel that provisions the card carries the whole rootfs, so it
grew to 10,332,036 bytes — inside the old 10 MB partition by 150 KB, which is
luck rather than margin, and the failure mode is a silently truncated kernel.
The kernel partition is now **12 MB** and `dtb` moved to `0xC20000`. Safe
because the bootloader walks the partition table rather than hardcoding
offsets; `make flash-all` reflashes both together.

## 4. Hot kernel text in internal SRAM

`patches/linux/0037-riscv-esp32p4-sram-hot-text.patch`. Mark a function
`__sramtext` and it is linked into a `.sram.text` section that lives in the
chip's internal SRAM instead of the cached PSRAM window; `_start_kernel`
copies it there from the kernel image before anything can call in.

The section has two addresses on purpose. Its VMA is the SRAM window, where
the code runs and where every pointer to it must resolve. Its LMA is the next
byte of the kernel image, so `Image` stays one contiguous blob —
`objcopy -O binary` orders by LMA, and a VMA-shaped hole would produce a
128 MB file. The bootloader needs to know nothing about it.

**Address, and this one is worth checking rather than assuming.**
`0x4FF40000`, the start of what ESP-IDF calls `sram_high`
(`esp_system/ld/esp32p4/memory.ld.in`). It is above every ROM-reserved range
— ROM download buffers, ROM startup stacks and ROM `.bss`/`.data` all end at
`0x4FF40000` on rev ≤ ECO4 — and below the L2 cache, which is carved out of
the *top* of the same 768 KB. With `CONFIG_CACHE_L2_CACHE_SIZE` at its 128 KB
default that leaves `0x4FF40000..0x4FFA0000`: 384 KB. The default budget is
128 KB of it and the link fails rather than overrunning into the cache.

**It requires `!RELOCATABLE`, and that is not packaging.** A relocatable
NOMMU kernel is linked at 0 and self-relocates to wherever it was loaded,
adding a fixed bias to every absolute address it finds. `.sram.text` must not
move with the image — it has a real fixed home — so the two schemes cannot
both be right. `arch/riscv/Kconfig` has

```
select RELOCATABLE if !MMU && !PHYS_RAM_BASE_FIXED
```

so the release is `CONFIG_NONPORTABLE=y`, `CONFIG_PHYS_RAM_BASE_FIXED=y`,
`CONFIG_PHYS_RAM_BASE=0x48000000`, and then `RELOCATABLE` off. That also
removes a whole relocation pass from boot.

Marked so far, all small leaf functions on the hottest paths: the CLIC
`mask`/`unmask`/`ack`, the systimer clocksource and `sched_clock` reads, and
the three ROM-thunk DMA cache hooks that run on every `dma_map`/`unmap`.

**Default `n`, and enabling it was a measurement rather than an assumption.**
Here is the measurement, same board, same card, same rootfs, kernels flashed
back to back:

| | baseline | `.sram.text` on |
|---|---|---|
| 30,000-iteration shell loop | 4 s | 4 s |
| 4 MB write, `bs=64k` | 2 s | 2 s |
| 1 MB write, `bs=4k` | 1 s | 1 s |

**No measurable difference**, which is the outcome the paragraph above
predicted: eight small functions that run constantly are exactly the ones the
L1 already holds. Getting a real answer needs finer instruments than
`date +%s` — a cycle-counter histogram on trap entry — and probably a bigger
`.sram.text` covering the whole exception path, which is the natural next
step now that the mechanism and its address map are proven.

**What did pay, and was not the point:** `.sram.text` requires
`!RELOCATABLE`, and dropping the PIE metadata is a real, measurable win on
its own.

| | relocatable | fixed at `0x48000000` |
|---|---|---|
| `Image` | 5,613,444 B | **4,501,212 B** |
| `MemTotal` | 21,248 kB | **21,912 kB** |
| reserved | 12,092 K | **11,000 K** |
| kernel rwdata / init | 981 K / 579 K | 371 K / 147 K |

1.1 MB off the image and 664 kB back into `MemTotal`, plus a whole relocation
pass removed from boot, for a kernel that has exactly one address it can ever
be loaded at anyway.

Verified on hardware — the section lands where it was aimed, and the board
boots and runs from it:

```
  [Nr] Name          Type      Addr     Off    Size
  [ 3] .sram.text    PROGBITS  4ff40000 8ca000 0001a8

4ff40000 t esp32p4_dma_cache_wback     4ff40116 t clic_irq_ack
4ff40040 t esp32p4_dma_cache_inv       4ff40142 t esp32p4_systimer_read64
4ff40080 t esp32p4_dma_cache_wback_inv 4ff401a4 t esp32p4_cs_read
4ff400de t clic_irq_mask               4ff400fa t clic_irq_unmask
```

**One bug worth recording, because the patch header predicted it and I still
walked into it.** The first build produced a **1.2 GB `Image`**. Every other
section in `vmlinux.lds.S` sets its LMA with `AT(ADDR(x) - LOAD_OFFSET)`, so
the image's LMA space is based at 0 while VMAs are based at
`CONFIG_PHYS_RAM_BASE`. Handing `AT()` a VMA-space value put `.sram.text`'s
LMA 0x48000000 above everything else and `objcopy -O binary` dutifully
zero-filled the gap — 1.2 GB from a 424-byte section. The fix is
`AT(__sram_text_lma - LOAD_OFFSET)`, and the segment table is the proof:

```
  LOAD  0x001000 0x48000000 0x00000000 0x2bcd40    <- everything else
  LOAD  0x2be000 0x4ff40000 0x002bcd40 0x0001a8    <- .sram.text, contiguous
  LOAD  0x2bef00 0x482bcf00 0x002bcf00 0x631828
```

## 5. The thing that cost the most time, and it was not a driver

Provisioning the card — getting 8.4 MB of rootfs onto it — failed three times
in ways that all looked like SD bugs and were not.

The provisioning kernel carries the rootfs as a built-in initramfs, so the
8.4 MB lands in RAM as **unevictable page cache** and never leaves. On a
32 MB board that is most of the budget, and `binfmt_flat` needs *one
physically contiguous* allocation per exec — 620 KB for busybox:

```
binfmt_flat: Unable to allocate RAM for process text/data, errno -12
nommu: Allocation of length 634880 from process 84 (id) failed
Normal: ... 3*512kB 0*1024kB 0*2048kB = 5268kB    <- largest block 512 KB
```

Commands stopped being able to start, mid-provision. Widening the pool to
12 MB to give the allocator more room made it strictly worse — that is 12 MB
`no-map` out of 32, and the kernel then OOMs before reaching userspace:

```
[    1.847255] Out of memory and no killable processes...
p4boot: reset reason 0x07 (MWDT (core))
```

Two lessons, both now in the DTS as comments:

1. **The pool serves `binfmt_flat`, not just anon mmap.** Patch 0010 hooks
   `do_mmap_private()`, which is the allocator every exec goes through. The
   old DTS comment said the opposite and sent me the wrong way twice.
2. **`timeout-sec = <30>` on the MWDT was a false-positive machine.** Nothing
   in this rootfs opens `/dev/watchdog`, so the feeds come from
   `watchdog_core`'s workqueue; one core plus a long stretch of hard I/O
   starves it, and a `mkfs` reset the board mid-format looking exactly like a
   driver hang. Now 240 s. The real fix is a userspace feeder — busybox
   `CONFIG_WATCHDOG`, one line in `board/busybox.fragment` — after which it
   can go back down and mean something.

None of this affects the shipping configuration: with root on the card there
is no initramfs, `MemTotal` is 21.9 MB with 17.7 MB available, and exec has
all the room it needs.

## Reproducing

```
cd bootloader
make flash-all                                  # table + kernel + dtb + bootloader
make flash-kernel KERNEL=../images/Image.sram   # the !RELOCATABLE build
make monitor                                    # console at 4 Mbps
```

To re-provision the card from scratch: flash `images/Image.initramfs`, then
from the board `mkfs.ext2 -F /dev/mmcblk0p1`, mount it, `cd / && cp -a bin
data etc init lib lib32 linuxrc media opt root sbin usr var /mnt/`, recreate
`dev proc sys tmp run mnt` empty, `sync`. Then flash `images/Image` back.
Expect exec failures during that copy — see §5 — they do not corrupt the
result, but check `df` before trusting it.

The SRAM build is not the default config; it is:

```
./scripts/config --enable NONPORTABLE --enable PHYS_RAM_BASE_FIXED \n                 --set-val PHYS_RAM_BASE 0x48000000 --disable RELOCATABLE \n                 --enable ESP32P4_SRAM_TEXT
```
